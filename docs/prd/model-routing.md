# 模型路由与订阅聚合

多个提供商模型组成路由并自动 fail-over、智能调度与额度感知；订阅接入的组合方式。订阅聚合仍受各供应商账户规则约束。

各段保留用户决定的原话与日期；同一主题下后来的决定修订先前的表述，以日期较晚者为准。来源见各段标注，产品入口见[产品定义](index.md)。

## 模型路由

2026-10-16 用户要求实现模型路由，验证场景为聚合两个 ChatGPT 订阅、自动 fail-over（[S30](../sources.md#s30)）。模型路由是网关配置中的显式条目：有名称和按优先顺序排列的若干提供商模型，与提供商模型一样出现在会话的模型选择中。选中路由时，网关按顺序选择成员；当前成员在尚未向调用方提交响应前失败且失败属于可切换类型时，自动改用下一个成员。直接选择某个提供商模型的请求不 fail-over。聚合多个订阅不表示额度合并或可规避供应商限制；每个成员仍受其自身账户规则约束。 本次验收使用用户已有的两个 ChatGPT 订阅；Codex Switcher 只是用户指出的验收凭据存放位置，不构成专用导入、格式适配或刷新集成的产品需求。 用户进一步明确：目标是类似 Magpie 的多订阅聚合能力，由 Velune AI 服务承载，不通过 Agent runtime 完成聚合；不以创建运行时实例或运行 Harness 作为使用多个订阅的前提。 用户已认可完整产品行为：Velune 内独立添加与维护订阅认证，多个订阅模型组成路由并自动 fail-over；可参考 yetone/magpie 与 Codex Switcher 的思路，具体方案随后已确认并授权 Rust lib 实施，平台前端由用户另行安排。 用户知悉双 ChatGPT 订阅自动轮换与 SIWC 规则存在冲突，仍要求保留该产品目标，并要求产品向使用者明确披露。订阅接入与路由配置应说明相关供应商限制，由使用者自行决定是否使用并承担相应风险；不宣称供应商认可，也不以开源身份承诺项目或维护者免责。 用户确认当前采用 Magpie／Switcher 所参考的 Codex 订阅接入思路；正式 SIWC 留作未来申请后的独立接入方向，不作为本轮交付前提。

## 调度、额度与使用上限

2026-10-16 后续用户要求继续实现智能调度、主动额度感知、使用上限、冷却与降序、会话黏性。保持一个订阅对应一个提供商实例：该实例持有自身认证、额度与使用限制，多实例通过模型路由聚合；不在提供商实例内增加订阅账户池。2026-10-17 用户确认实施以下方案，仍限定 Rust lib；实现与验收状态归任务记录。

路由支持智能、顺序、轮询、权重四种策略。智能模式先保留仍有资格的会话绑定，需要重新选择时，按各实例最紧额度窗口中距离使用上限的相对余量排序。选择依次执行资格与上限检查、冷却检查、会话黏性、策略排序及既有提交前失败切换；轮询和权重在启用黏性时主要分配新会话。额度首先接入 ChatGPT 订阅，主动按需刷新，区分有效、过期、未知及不支持。实例可配置各窗口的已用百分比阈值，达到任一适用阈值就暂停新请求；所有路由和直接调用共享实例限制。有上限且无法取得新鲜额度时暂停，无上限的未知额度实例可作为后备。

限流及暂时故障进入冷却，全部候选冷却时返回可重试时间，期满只允许一个请求探测，恢复后重新参与正常排序。会话身份由调用方明确提供，替补成功后更新绑定；黏性不得绕过健康或使用上限，首版只保证同一应用运行期间、跨 Runner 保留。使用上限依据供应商观测暂停新请求，不保证外部并发和在途请求精确不越线；到重置时刻需重新观测，不能推定额度已经恢复。此阶段不增加重置节奏预测、跨重启黏性或新的流缓冲，保留成功响应 headers 交付后不切换的边界。

## 订阅接入

2026-10-17 用户进一步要求订阅接入按 LLM 协议、认证与额度等能力组合，避免为每个品牌建立贯穿系统的提供商类型；一个订阅一个实例的归属不变。下一步目标是 Claude Code 订阅，先研究 Magpie 与供应商接口，辨别公共机制与专属适配，再确认具体解耦方案；不把品牌名单视为已验证兼容承诺。

2026-10-17 用户随后确认实施组合解耦，并明确接受 Claude 订阅依赖本机 Claude Code，纳入进程、会话和工具桥接。Claude Code 作为提供商成员的执行后端，聚合、选择和 fail-over 仍归 Velune 网关；不要求用户把聚合建模为 Agent runtime 配置。Claude 原生认证流程持有凭据与续期；工具执行权保持在调用方，后端可能已执行的请求不得仅因下游未发响应头而自动重放。继续限定 Rust lib，前端另行实现。

2026-10-20 用户认可 Kimi Coding Plan 采用“提供商模板、主动额度适配、服务错误语义适配”的方向；账户/额度只读验证和方案收敛后，明确要求开始实现。Kimi 订阅仍作为一个提供商实例，通过官方 Coding API Key 直连，无需安装 Kimi CLI；同一会员创建的多个 Key 不构成多个订阅。具体接口权限、账户归属与验收证据归任务记录，不将个别 Key 的成功探测提升为所有套餐的兼容承诺。

2026-10-20 用户确认 ARK Coding Plan 采用“在提供商内部独立配置额度查询认证”的方案并授权实施。模型请求与额度查询使用各自认证，不新增中央认证实体或贯穿系统的品牌类型；范围先为国内个人 Coding Plan。查询凭据与模型订阅的关联由用户显式确认，产品不得把成功读取额度称为已自动核验同账户，仍保持一订阅一提供商的归属要求。
