# 远程控制与多设备

同一个人的多台设备经公网或局域网互相控制；完整端与控制端的分工。传输与配对契约见[远控设计](../design/remote-access.md)。

各段保留用户决定的原话与日期；同一主题下后来的决定修订先前的表述，以日期较晚者为准。来源见各段标注，产品入口见[产品定义](index.md)。

## 范围与连接

2026-10-17 用户明确远程控制覆盖同一个人的多台设备，通过公网使用，不要求用户先配置 VPN 或端口转发。远程端应覆盖 Velune 完整业务能力，包括会话、审批、模型／运行时／资源配置和变更查看；这不自动包含独立终端或通用文件管理。执行宿主同时面向有 GUI 的应用与无 GUI 的应用，两者装配同样的共享核心，远控契约不因 GUI 的存在而分叉。当前委托先共同梳理需求与架构，再实现相应 Rust packages；具体传输、设备信任、断连和并发语义仍需收敛，不能据此宣称远控已经交付。来源见 [S40](../sources.md#s40)。

用户随后确认：控制设备断网、退出或进入后台后，执行端继续工作，待答审批保留，其他已配对设备可接续操作；这不表示执行应用退出、机器睡眠或断电后仍能运行。公网连接最终提供开箱即用的服务，同时允许自部署。当前 Rust 实现不包含公网服务部署或正式中继可用性承诺。

远控应尽可能在无需持续数据中继的直连路径上保持稳定。2026-10-17 用户同意采用 iroh，同时要求参考、对比 ds-harness-remote 的 WebRTC／TURN 实现经验；建联协调、地址发现与持续数据中继分别说明，不把远控稳定性等同于只能依赖中继。

用户随后确认允许使用 iroh 公共设施，并允许切换到自部署或其它兼容所用 iroh 协议的公开 relay。公网与局域网共用设备列表、添加、授权和重连体验，不要求用户选择两种远控模式。同一设备的身份与信任不因地址、网络或 relay 变化而改变；Direct／Relay 是连接状态，不是设备类别或业务入口。来源见 [S40](../sources.md#s40)。

用户进一步要求多路连接与自动优选：在公网中使用及进入同一局域网后，系统能发现可用路径并自动选择更优路径，离开局域网后继续恢复，不要求用户重新连接或切换模式。具体路径探测、选择与稳定性机制由技术方案核实，不把统一界面等同于已经实现多路径切换。来源见 [S40](../sources.md#s40)。

## 配对与端

用户认可手机扫码、Mac 确认、建立持久信任后自动重连的配对方式。二维码是添加设备的交互入口，不把原始邀请 JSON 作为正常用户流程；该认可不排除无 GUI 宿主，也不提前确定异地首次添加或账户恢复机制。来源见 [S41](../sources.md#s41)。

同日用户授权实现最小 Android 端，采用 Kotlin／Jetpack Compose，并允许使用已连接 adb 的真机进行验收和实验。同 Wi‑Fi 的设备可用于安装、直连及业务闭环验收，不作为公网可达性证据；最小界面切片不缩窄共享远控 SDK 的完整业务范围。来源见 [S41](../sources.md#s41)。

2026-10-18 用户将当前实施责任明确限定为 Rust Library，包括 UniFFI 契约与库级验证；Mac／Android App 接入、界面与安装由独立平台工作承担。此边界不撤销统一远控和最小 Android 的产品目标，也不能用库验证替代整机网络或界面验收。来源见 [S41](../sources.md#s41)。

## 远控 MVP

2026-10-19 用户发起远控 MVP，并解除上一条“仅 Rust Library”的实施边界。设备分两类：完整端（Mac、Windows）运行 agent runtime，也能控制其他端；控制端（Android，将来的 iPad、Web）只有控制能力，不运行 agent runtime。任何一端都能控制其他端。各端界面只编写一份，本机与远端设备经同一业务接口访问，由用户选择目标设备。远程控制与 SSH 运行时是两项独立能力：前者是另一台 Velune 设备的界面操作本机，后者是本机核心在远端机器上执行 Harness。MVP 先交付会话日常闭环（会话列表与转录、发送、停止、审批／问题）。提供商、资源等配置的目标是跨端同步，而不只是远程编辑；同步语义与秘密边界仍待方案收敛。MVP 使用 iroh 公共 relay。Windows 端须在本机运行 agents。来源见 [S43](../sources.md#s43)。
