# 来源：输入选择、恢复与状态身份

[返回来源索引](../sources.md)。本页保留原始决定与当时的授权边界；它不是当前实现状态或本次任务的授权清单。现行规则从[文档入口](../index.md)按主题查阅。

## S20

2026-10-13 用户要求继续改进 composer 的运行时、模型、推理、权限选择器（并指出它们在深色模式下没有跟随系统外观），发送后立即在消息列表中显示用户消息与“发送中”之类的状态，以及可以查阅各 turn（含当前 turn）使用的配置。用户选择“两个下拉”的组织方式，并选择在工作过程行右侧显示轮次配置，同时要求再收拢：悬停时展开，或保留一个 plain 图标按钮。同日用户验收新样式后指出下拉的三角离标题太近，且“运行时 · 模型 · 推理强度”下拉的选项太长、太复杂，建议考虑二级菜单等方案。产品归[选择与状态](../prd/composer-choices.md#选择器与下一轮选择)与[提交反馈](../prd/composer-actions.md#提交主按钮与即时反馈)，实施归 composer 与轮次配置任务（git 历史：tasks/composer-turn-settings）。

同日实测 Claude Code 2.1.286 恢复会话时沿用上次的权限模式（CLI 没有“回到默认”的取值），Codex 的轮次覆盖在 Velune 的托管路径下不会保留。用户据此选择“沿用会话当前模式”，不读取 Harness 配置来回到默认。

## S21

2026-10-13 用户验收 composer 子菜单后提出下一批改进：composer 的选择进一步按运行时保存，切换运行时而未发送时回到当前／上一轮使用的运行时；推理强度不做本地化，按实际发给运行时的值显示；询问推理强度的“默认”是否真的发送 `default`；轮次配置悬停时只显示运行时与模型，详情增加该轮 usage（特别要包含 reasoning tokens）；此前认为资源库不需要把原生改动回填到资源，实际使用后认为需要。助手说明“默认”不发送任何值、三种 Harness 结果不一致后，用户选择推理强度与权限模式一样“沿用会话当前”，并补充模型也应默认跟随当前／上一轮；对“未发送的选择离开会话后是否保留”，用户选择只有运行时回到最近一轮，各运行时的选择（含配置）按运行时保存。产品归 [PRD](../prd/composer-choices.md#选择器与下一轮选择) 与资源库段落，实施归 composer 与轮次配置任务（git 历史：tasks/composer-turn-settings）。

## S22

2026-10-14 用户验收 S21 各项后，要求在 composer（会话详情视图）中增加 status line，出发点是显示上下文用量，可按需扩展。三种位置方案（composer 下方状态行、操作行右侧紧凑显示、窗口底部状态栏）中用户偏好操作行右侧的紧凑方式，依据是避免信息过载、保持界面干净，同时不损害信息披露，并表示三种都不完全满意。其余候选（本会话累计 token、工作目录与 git 分支、Codex 账户额度、Harness 报告的费用）都可以有，但建议默认不放入 status line，由用户在会话设置中自定义；重点是位置与呈现方式。产品归 [PRD](../prd/composer-choices.md#status-line-与用量显示)，实施归 status line 任务（git 历史：tasks/composer-status-line）。

## S27

2026-10-15 用户确认窗口系统的标签修复后要求实现：编辑用户消息——可以编辑任意一条用户消息，但编辑上一条之外的用户消息会询问是 fork 会话继续还是原地继续；支持消息发送队列、steering；支持 interrupt／continue session。就助手的提问，用户对“interrupt／continue session”选择“只要‘继续’”（中断沿用停止生成，只增加停止或失败后的“继续”）；对队列与 steering 的呈现选择“默认排队，可改 steer”。产品归 [PRD](../prd/composer-actions.md)，实施归 消息编辑与发送队列任务（git 历史：tasks/message-editing-queue）。

## S39

2026-10-18 用户要求：“让额度可以显示为‘剩余多少’（目前是‘使用了多少’），对于 context window 也是一样；我建议这放到‘通用’或者‘外观’（目前还没有）设置 Tab 中（我还建议将会话、快捷键都合入该 Tab 中）”。开发方以一项“已用／剩余”设置同时作用于额度与上下文，新建“通用”页并将会话、快捷键并入。产品归 [PRD](../prd/composer-choices.md#status-line-与用量显示)。

## S42

2026-10-18 用户指出：“claude code 的 session 中，模型的“沿用”似乎不太行（我这边看到推理仍然是 medium，但是模型是 default）；不过其实，我一直都没有太具体地管理 runtime, model, thinking, permission 的行为，我们现在来讨论、整理一下”。开发方核对：Claude 历史已读出模型、推理强度与权限模式；模型显示不对，是因为记录中的完整模型 ID 与目录里的别名对不上，Mac 于是改用目录第一项；下一轮的选择也只在内存中按标签页保存。开发方提议各项分“会话当前”与“下一轮的选择”两层、未知时不发送，并就持久化与新会话默认提问。用户答复：“composer 的状态是持久化的，也就是说，重启之后，下一轮的选择要保留”；“新会话的默认值，默认使用上次选择的，但是也可以在运行时实例中设置”；“我同意你的建议，按照你的建议处理就好”。实施中用户补充：“运行时实例中，还可以选择让新会话的默认值使用运行时的默认值；并且我认为所谓的“默认值”，其在 velune 内部应该是 null（避免用"unknown","native"）”。产品归 [PRD](../prd/composer-choices.md#选择器与下一轮选择)，实施归 composer 轮次配置任务（git 历史：tasks/composer-turn-settings）。

## S54

2026-10-26 用户：“Codex 从某个时候开始支持在 interrupt/stop 会话之后 resume 而不需要发送另外一条消息，你看 codex app-server 的协议，是否有这样的功能，有的话，我希望让 Velune 支持它（并且最好看看目前的其他几种 agent runtime 能否也都支持）”。授权按协议证据接入无新用户消息的恢复，兼查其他运行时；本条修订 [S27](#s27) 对“继续”始终发送用户消息的统一实现。产品归 [输入区](../prd/composer-actions.md)，实现与验证归 原生恢复任务（git 历史：tasks/native-turn-resume）。

2026-10-27 用户指出“会话进行时继续按钮可以使用”“没有发现继续和发送的互斥关系”，要求重新思考；随后对单一发送／排队／继续主按钮、停止独立、草稿与继续互斥、去掉文本 fallback、统一命令入口和核心资格的方案答复：“可以，别忘了更新文档。”本条修订前一版无原生能力时自动发送文字继续的行为。

## S62

2026-11-02 用户要求细化 composer 状态：单栏即使使用 bottom drawer，也应具有按会话“切换”的感受；分屏共用输入区时移动焦点、将 B 换成 C 都保留共享草稿，只改变目标；只整理布局时，当前文字、附件和明确选择继续可见。用户整体同意包含布局连续性、冲突草稿保留与就地切换、状态归属和恢复规则的产品方案，并建议将此次经验沉淀为 UI common pattern，归 [DESIGN.md](../../DESIGN.md#未完成工作的连续性)。

同次用户指出锁定 UI 修复造成编辑回退：本应只禁止发送，草稿仍可编辑；认可用“已锁定”替代发送按钮。另要求一并修复侧聊标签未命名、侧聊不能切换运行时／模型等选择、输入框与 bottom drawer 无法缩至一行，以及 429／频率限制自动重试。行为归[内容与导航](../prd/composer-input.md)、[锁定与恢复](../prd/composer-actions.md)和[侧聊](../prd/conversations.md#侧聊)。

## S70

2026-11-03 用户在 dogfood 后修订 composer 的状态规则：“在 group 内切换 tab 时，composer 状态跟着 tab 走；切换聚焦 group 则不然。”用户指出规则已经复杂，要求重新整理，并弄清 state key 的组成。该要求修订 S62 中“分屏共用时换标签也只改发送目标”的表述；往返恢复、其他导航与状态身份的推导须与用户明确的新要求区分。能力归[输入区](../prd/composer-input.md#内容与目标的归属)与[工作区布局](../prd/workspace-layout.md)。

## S71

2026-11-03 用户认可 composer 的输入身份／导航恢复／发送目标三层模型，并澄清讨论的状态一直是“正文、附件、运行时与模型与权限选择”。用户要求这些状态跨设备同步，指出只有一个用户，许多并发协作问题不必考虑；同时明确“新建会话也是独立的状态（但是全局只有一个‘新建会话’的状态）”。这修订此前按客户端设备隔离输入及每个新建入口分配独立输入的前提，不自动表示已确认全部转换推导或已有实现。行为归[输入区](../prd/composer-input.md#内容与目标的归属)，跨设备范围归[远程控制与多设备](../prd/remote-access.md#composer-状态接续)。
