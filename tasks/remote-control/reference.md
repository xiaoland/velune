## 上游实际覆盖与缺口

- **上游产品文档声称**：手机、PC、Web 进入工作机上的同一个 Harness；P2P/TURN 不通时用 Server Relay；支持会话、只读文件、终端和更多 Harness（[README.zh.md](https://github.com/liguobao/ds-harness-remote/blob/d1a311254a7f3031265550840564bc93c2faf9ca/README.zh.md#L28-L52)）。这是产品宣称，不等于整个链路在此提交都有实现或已完成真实网络验收。
- **仓库边界声明**：协议文档说当前仓库实现 Client/Plugin 与最小单账号 Relay Server；多账号、WebRTC/TURN 属于独立 Server（[protocol.md](https://github.com/liguobao/ds-harness-remote/blob/d1a311254a7f3031265550840564bc93c2faf9ca/docs/protocol.md#L1-L25)）。实际自部署 README 也只列设备注册、刷新、发现、Control 和 E2EE Relay，单进程持久化；没有 TURN 或 P2P（[apps/server/README.zh.md](https://github.com/liguobao/ds-harness-remote/blob/d1a311254a7f3031265550840564bc93c2faf9ca/apps/server/README.zh.md#L1-L22)、[L53-L57](https://github.com/liguobao/ds-harness-remote/blob/d1a311254a7f3031265550840564bc93c2faf9ca/apps/server/README.zh.md#L53-L57)）。源码 Gateway 对连接只接受 relay，且 signaling 不转发（[gateway.ts](https://github.com/liguobao/ds-harness-remote/blob/d1a311254a7f3031265550840564bc93c2faf9ca/apps/server/src/gateway.ts#L117-L158)）。因此宣传中的全球多 TURN 依赖仓库外的托管服务/组件，不应当作可复用的当前仓库 Server 实现。
- **Client 成熟度边界**：VS Code 文档把自己标为 developer preview，明确实时流、自动重连、问题回答 UI 尚在开发；测试仍进行跨机器扩展 Host（[apps/vscode/README.md](https://github.com/liguobao/ds-harness-remote/blob/d1a311254a7f3031265550840564bc93c2faf9ca/apps/vscode/README.md#L1-L40)）。网络设计文档也说网络切换的已建立连接不会无缝迁移，当前关闭旧逻辑连接并重新建链；重连后重读原生 history baseline，不自动重发结果未知的 mutation，stream 自动重开及长期跨网验证尚未完成（[network.md](https://github.com/liguobao/ds-harness-remote/blob/d1a311254a7f3031265550840564bc93c2faf9ca/docs/network.md#L161-L173)、[L190-L199](https://github.com/liguobao/ds-harness-remote/blob/d1a311254a7f3031265550840564bc93c2faf9ca/docs/network.md#L190-L199)）。

## 持久化、重复请求、审批与并发

- **持久化归属**：Relay Server 不存 prompt/session；业务 session 留在 Host Harness。Server 只持久化设备凭据与公钥描述；自身重启会丢连接 presence，Host 必须重新连。故“同一个 session 跨设备回来”依赖 Harness 原生 session 可恢复，不依赖 Relay 保存消息。
- **断线/重复发送**：每个 request 有 correlation ID 和一个 response/error；request timeout 后丢弃迟到回复，结果未知时禁止盲目重发 mutation。恢复时重新握手和开流、读 history baseline；这避免重复创建/发送造成二次副作用，但用户可能需要判断上一次操作到底有没有生效（[protocol.md §16.3](https://github.com/liguobao/ds-harness-remote/blob/d1a311254a7f3031265550840564bc93c2faf9ca/docs/protocol.md#L730-L751)、[network.md §8](https://github.com/liguobao/ds-harness-remote/blob/d1a311254a7f3031265550840564bc93c2faf9ca/docs/network.md#L161-L173)）。部分独立能力（如 Codex project/create）另带 idempotency key；不能推为所有 mutation 都可重试（[protocol.md](https://github.com/liguobao/ds-harness-remote/blob/d1a311254a7f3031265550840564bc93c2faf9ca/docs/protocol.md#L1300-L1314)）。
- **审批**：审批响应绑定发起连接、Host 上游请求和临时 handle；断线/重配/过期后旧 handle 失效，未知 owner 的审批 fail closed，只支持明确的单次允许/拒绝，不广播给其他设备或恢复为长期授权（[protocol.md](https://github.com/liguobao/ds-harness-remote/blob/d1a311254a7f3031265550840564bc93c2faf9ca/docs/protocol.md#L1238-L1258)、[L1350-L1365](https://github.com/liguobao/ds-harness-remote/blob/d1a311254a7f3031265550840564bc93c2faf9ca/docs/protocol.md#L1350-L1365)）。
- **多端**：新 Host 实现允许不同 Client device 同时保持独立连接，按 connection 隔离 RPC/stream；同一 client device 重连替换自己旧连接。Codex mutation 另有 active-turn lease：一个 connection 拥有写入/审批，其他 peer 不能抢占；协议明确不同 client 同时连通，不等于所有 Harness 后端都有通用读者/写者租约（[protocol.md §11](https://github.com/liguobao/ds-harness-remote/blob/d1a311254a7f3031265550840564bc93c2faf9ca/docs/protocol.md#L501-L515)、[Codex](https://github.com/liguobao/ds-harness-remote/blob/d1a311254a7f3031265550840564bc93c2faf9ca/docs/protocol.md#L1350-L1365)）。最小仓库 Server 对较旧 Host 采用 last-client-wins（[gateway.ts](https://github.com/liguobao/ds-harness-remote/blob/d1a311254a7f3031265550840564bc93c2faf9ca/apps/server/src/gateway.ts#L117-L149)）。

## 对 Velune 的迁移判断

**可借鉴**：控制面与业务加密数据面分开；Host 主动出站；transport 是可替换底层而不是业务协议分叉；session authority 留在实际 Harness；每连接独立 ID/请求/事件所有权；不确定 mutation 不自动重试；审批句柄绑定具体请求及设备；撤销要实时关闭已有连接；E2EE 与能力 allowlist 同时存在。

**不应默认照搬**：DeepSeek 专有协议/Native UI、插件登录/同账号自动授权、服务端必须上云、全球 TURN、E2EE 一定要采用 Noise IK、公网上的多租户 Server、终端/文件/通用 RPC、多端写者并行。它们会扩大兼容面、部署和安全运维责任；用户需要先确定使用边界。DSH 的同账号自动 membership 简化体验，但也意味着任何登录同账号设备能尝试连接，不能代替 Velune 的设备逐一授权需求。

**Velune 的已知硬约束**：现有项目决定 Rust core 同进程嵌入原生 App，不启动独立常驻 core/Host 或 App↔Host socket。若产品要求 GUI 退出后 Host 仍可接入，需要单独常驻宿主，这会改变现有架构边界；若只要求 Velune 运行时让另一端接管当前本机 Harness，可在该进程内承载 Host 会话与 transport，不需要复制 Harness 会话数据库。常驻宿主也不能解决 Mac 睡眠、断电或网络不可达：这些情形分别需要机器保持唤醒/供电、网络恢复或额外的远程唤醒前提。跨 LAN/VPN、公网协调、Service/TURN 的部署责任及是否自建均是尚未确认的产品取舍。

## 需和用户收敛的最小问题

1. **谁连谁、在线条件**：手机/另一台 Mac 连到运行 Velune 的 Mac；Host 是否必须在 GUI 退出后继续运行？这决定是否需要常驻宿主。机器睡眠/断电时是否仍要求可用是另一个问题，常驻进程无法单独满足；需要明确机器保持唤醒/供电或采用何种网络唤醒前提。
2. **第一版操作权限**：只看/继续既有会话并发消息、创建新会话是否都需要？文件浏览、终端、任意 Harness 配置是否明确排除？建议初版限会话浏览/交互与原生审批，沿用 Harness authority。
3. **网络和服务**：第一版仅 LAN/VPN，还是离家也要用？若公网，是否接受账号/设备协调服务与 Relay 的运营、数据元数据和带宽成本；是否要保证无 UDP 环境可达？
4. **信任与多端规则**：逐设备批准/可撤销，还是登录同一账号自动互信？多个端同时只读可以，写操作采用单 active controller lease，还是允许同时发 Prompt？当执行结果未知，建议不自动重发并明确显示“结果待确认”。

### 官方协议核查

2026-10-17 检查：[RFC 8445 ICE](https://www.rfc-editor.org/rfc/rfc8445.html)、[RFC 8489 STUN](https://www.rfc-editor.org/rfc/rfc8489.html)、[RFC 8656 TURN](https://www.rfc-editor.org/rfc/rfc8656.html)、[RFC 8838 Trickle ICE](https://www.rfc-editor.org/rfc/rfc8838.html)、[Noise Protocol Framework](https://noiseprotocol.org/noise.html)。它们说明网络穿透/中继和端到端安全协议的机制；不能据此推定 Velune 的账号、设备授权、运行时长或产品权限。

## WebRTC 直连机制与 iroh 1.3.0 对照

增补检查日期：2026-10-17。DSH 源码固定为上文提交 `d1a311254a7f3031265550840564bc93c2faf9ca`；iroh API 与实现按官方 `1.3.0` 文档/源码核对，该版于 2026-09-28 发布（[release](https://github.com/n0-computer/iroh/releases/tag/v1.3.0)，源码提交 `0072d7d`）。

|---|---|---|---|

| 直连、候选与中继顺序 | DSH 的首轮 direct 只配置 STUN URL，按 `lan → p2p → relay` 协商；STUN 提供 NAT 映射地址候选，不保证 NAT 间一定可达。超时/失败后关闭这轮连接，再开一轮含 TURN 的 `turn → relay`，再失败才新建纯 Relay 轮次。同一轮内部的 ICE 候选收集/连通性检查仍由 ICE 处理；**外围的 direct/TURN/Relay 轮次是顺序重试**。direct 的应用层协商限时 12 秒；一般 ICE 配置读取上限为 10 秒，RTC 通用超时默认 8 秒。ICE server 获取失败不会立即放弃，会继续用 host candidates 尝试。顺序重试会为减少 TURN 使用付出最坏冷建链时延，不是 direct 与 TURN 两套 PeerConnection 同时竞速（[client-connection.ts](https://github.com/liguobao/ds-harness-remote/blob/d1a311254a7f3031265550840564bc93c2faf9ca/packages/plugin/src/client-connection.ts#L81-L145)、[adaptive-transport.ts](https://github.com/liguobao/ds-harness-remote/blob/d1a311254a7f3031265550840564bc93c2faf9ca/packages/webrtc/src/adaptive-transport.ts#L336-L388)、[L401-L485](https://github.com/liguobao/ds-harness-remote/blob/d1a311254a7f3031265550840564bc93c2faf9ca/packages/webrtc/src/adaptive-transport.ts#L401-L485)、[stunOnlyIceServers](https://github.com/liguobao/ds-harness-remote/blob/d1a311254a7f3031265550840564bc93c2faf9ca/packages/webrtc/src/rtc-adapter.ts#L169-L183)、[RFC 8445](https://www.rfc-editor.org/rfc/rfc8445.html)）。 | iroh 的常规模式以配置的 home relay 建连并协助 hole punching，直接路径打开后选择直接路径，relay 可留作备用；无法直连时仍可走 relay。`RelayMode::Default` 表示使用默认 n0 relay 配置，不表示禁用 relay。`RelayMode::Disabled` 会移除该可用性后备；要不用 AddressLookup/relay，调用方须已经掌握足够且可达的 `EndpointAddr`（[RelayMode](https://docs.rs/iroh/1.3.0/iroh/endpoint/enum.RelayMode.html)、[Endpoint](https://docs.rs/iroh/1.3.0/iroh/endpoint/struct.Endpoint.html)、[iroh 1.3.0 path selector](https://docs.rs/iroh/1.3.0/src/iroh/socket/biased_rtt_path_selector.rs.html)）。 | “直连成功”受双端 NAT/防火墙/UDP 策略影响，ICE 或 iroh 都不能由应用代码保证。初期用 iroh 默认发现/relay-assisted 建连并测量实际选路；除非产品另作选择，不先禁用 relay 来追求表面上的“无中继”。iroh relay 与 WebRTC TURN 是不同协议服务，不能把 DSH 的 TURN 配置直接移植成 iroh relay。 |

这里有两个独立的“无中继”指标：**无持续数据中继**是连接建立时可用 relay 协调/hole punch，之后业务字节走 direct path；iroh 默认架构能尝试这种路径提升，但要以 selected path/统计验证。**无协调/发现服务**则要求端点通过其他可信渠道已知对端可达地址；只给 EndpointId 时仍依赖 AddressLookup，禁止 relay 且地址不可达时会失败。直连受限时，中继是可用性回退，不应把它计为直连成功。

### 对 iroh 实施的具体动作与判别实验

1. **默认路径先测而非自定义。** 使用 iroh 1.3 默认 relay/discovery，持有 `Connection::path_events()`；把事件和 `paths()` 快照映射为连接诊断，记录首条 direct path 出现时间、selected path、地址族、RTT、连接关闭原因及本次/累计 relay 流量。比较建连当下 relay 与直连稳定后数据所走路径，直接判定“免持续中继”是否达到，而不是由握手成功推断。
2. **独立验证不依赖发现服务的条件。** 同一对测试端先传递完整 `EndpointAddr`、用 `RelayMode::Disabled` 在同 LAN 与具备公网可达地址的网络验证直接连接；再只传 EndpointId 并禁用 AddressLookup/relay，确认缺少可达地址时按预期失败。该组验证拆开“数据不经 relay”和“完全没有协调服务”，避免把两者写成一个产品承诺。
3. **验证切网和恢复语义。** 记录现存 Connection 的 path events，同时将端点从 Wi‑Fi 切至手机热点；平台能观察网络变化时调用 `Endpoint::network_change()`。检查是否原 connection 选择新 path、是否发生短暂无数据、还是 connection 结束后需 `Endpoint::connect` 新建。端到端同时检查请求 ID、结果未知的 mutation 不重发、审批句柄在连接替换后的行为。
4. **覆盖真正决定直连率的网络组合。** 最小矩阵包括同 LAN、两个家用 NAT、IPv4-only/双栈/IPv6-only（若产品平台支持）、蜂窝/CGNAT，以及显式封锁 UDP 的网络；分别记录 direct 建立率、首连 p50/p95、path promotion 时间、relay fallback 占比和网络切换后恢复时长。ICE candidate 收集、STUN、hole punching 和路径竞选能提高可达率/更快找到可用路径，TURN/relay 能覆盖部分直连失败；NAT 行为或防火墙彻底阻止双方可用的直连时，应用逻辑无法保证直连，必须依靠被该网络允许的 relay/其他传输或承认不可达。

建议作为 iroh 实施验收的首个可证伪问题：在常见异网条件下，默认配置能否先建立连接、随后观察到 direct selected path，并在 Wi‑Fi 切网后同一连接恢复或给出明确可恢复的关闭信号？如果前半项失败，优先检查 endpoint 地址发现、relay 可达性和网络类型；如果只在切网失败，再定位 path 重评、网络通知与应用层 stream 重建，不要先换掉 transport。
