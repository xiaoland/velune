重审修复了 ACP 打开失败后暴露未确认历史、Pi 编辑丢失错误原因、Mac 新标签草稿身份不一致、分叉编辑丢失已选模型和多设备列表拖放选错来源的问题，也修复了 iOS 预览不能真实选择运行时。团队从正常调用者重新建立协议、存储、生成绑定和平台验证，撤掉测试独占的生产端口与写入器。首轮的 Pi 背压、IPv6 端点、Claude 空会话恢复等独立修复继续保留。[首轮证据](audit.md)

## 独立复核与对照

- 缓存故意移除字节限制、将数量限制从 8 改为 7，旧验收都通过。新验收分别在目标观察失败。让摘要失败返回另一错误码也得到旧绿、新红。恢复源码并重新构建后两个绑定场景均通过。
- 让验收父进程接受其它用例身份、或将 exit 0 的业务失败改写为成功，各得到旧绿、新红、还原绿。保留生成模块与库版本核验、真实子进程和产物清单。
- 将运行时策略的备份字节替换为 `{}`，或只把预期的策略冲突诊断换为无关前置错误，旧迁移检查都通过、新检查都失败。恢复后三个迁移检查通过。实际文件的原始期望取自产生迁移前。
- Pi 的过期摘要故意返回无关错误，旧 SDK 删除脚本通过，新脚本在原因断言失败；正常 SDK 上的删除、编辑、通知取消三个脚本均通过。Pi 插件检查还单独破坏了旧插件本轮回复、SDK 加载与 stop 回应；原检查把错误算作成功，新检查命中对应阶段。
- 独立检查删除的 Rust 覆盖时，找回 Claude 9 MiB 消息的完整协议帧、侧会话写入 context.txt 并连续提问、模型/effort/自动压缩启动参数与清除行为。这些已迁到实际 NativeSession。Mac 复核找回共享 ToolHeader 的动作和几何边界、原生项目目录拒绝条件及退役参数的显式退出。
- 控制旧运行库的对端先返回一段历史，再以固定 RPC 错误拒绝加载。修复前 `load`、`resume` 都报告拒绝却使 `snapshot()` 暴露 `synthetic-acp:rejected`；两项在读取该未经确认身份时各自失败。采用协议的通用内部错误码使该对照与另有专属类别的认证失败可区分。
- 在保留的 Codex 上下文检查中恢复了 `inter_agent_communication` 这个易与元数据混淆的负向参数。将只允许 `inter_agent_communication_metadata` 改成允许同前缀的一族记录，真实 Python helper 会静默接受含正文的未知记录。恢复精确相等后在该记录处拒绝并无上下文输出。
- Linux 的默认测试还暴露了两处真实 Pi 诊断丢失。编辑回退所收到的 SDK 错误原先变成了笼统的“未能回到这条消息之前”；已观察到的写入超时在进入清理分支后变成了“连接需要清理”。保持原生原因的修复位于 PiSession 的回执与回退结果处理处，验收同时保护源历史与后续 prompt。

## 合成会话、独立期望与回归对照

- 两项安装版 Pi 检查原来递归复制外部目录并从活动历史或备份中挑选文件。同一条命令可能因该目录的先前状态而换输入。现在仓库随附 Pi 1.4 SDK 写出的三轮合成会话。每个场景新建目录，应用检查先读到六条已知正文，再删除、截断和冷读；运行时检查还统计回环模型服务实际收到的请求。两项验收共用输入，分别打开自己的进程和文件。
- 在应用层逐一撤回环境变量清理、用量回退、已兑换条目保留、旧指纹编码、草稿归属与模型选择、关联格式拒写、关联全量迁移、手工读状态的 wire 编码、无数据 profile 准入、嵌套未知字段拒写。11 组候选通过，11 组在目标断言失败，恢复后均通过。迁移组实际关闭并重开，丢掉第二条记录会使 Unicode／来源不同的关联消失。六个受控源文件逐字节还原。
- Linux 回归运行中修正了三处测试前提。相同网络设置可以保持持久化 revision，新夹具只改超时时长，随后观察保存值及新 generation。远端服务在关闭后不再提供 descriptor，新夹具先取得合法快照再执行关停和 CAS。Pi 编辑失败会在原生历史后合法追加一条系统通知，新断言要求完整原始消息保持原序、末尾仅追加对应原因。
- 已安装 Codex 在 0.171.0-alpha.13 上实际完成模型档位选择、摘要、MCP 隔离、队列与恢复。旧显式测试在运行适配器前只接受 0.167，实际二进制因该硬编码直接失败；候选使用适配器自己的版本准入和私有子进程环境。两个原生导入回归同时通过，缺失 provider 的负向检查核对错误中出现被拒的 provider 身份。
- 缓存回收的四种拒绝场景共用退出码 2。把 Cargo 锁的诊断换成无关原因、或让平台锁拒绝前先截断目标文件，旧检查都通过。新检查逐项核对平台／锁路径／符号链接原因以及原产物完整字节，两次都在对应断言失败，恢复后分别通过。

Mac 分叉测试发现打开新标签与保存编辑配置会竞争。先让另一个客户端准备分叉，目标会是 revision 1 的默认配置；旧 owner 此时保存已选模型会报冲突。新 owner 通过既有 EnsureTarget 原子填入默认项，读回 revision 2 与固定模型。另一个客户端真正改选后仍应提示冲突并保留对方选择。真实编辑窗口在浅、深两种主题下，关闭或切换标签后也能由第二个 Core 客户端读到已接受的配置。
