## 为什么保留其它边界

内容身份、目标配置、窗口布局具有不同的真实变化原因。同 group 切 Tab 更换内容，跨 group 移焦点只更换执行目标，整理布局不产生新输入。因此保留 InputID、ContextKey 与窗口呈现的三层边界，删除的是绕过这些边界的旧实现。

原生 Harness 仍拥有历史，application 拥有业务准入与请求生命周期，平台拥有输入法、视图焦点和本地提交中状态。把全部内容合并为一个总状态机，会迫使核心理解平台输入细节。队列的“现在显示排队”与“迟到的排队请求可以被接纳”也必须分别表达，停止后已发出的请求会被保留为暂停项，不能因 UI 已变为空闲就丢弃它。

## 结构验收依据

这轮的结果同时要求行为保持和旧协调消失。输入治理检查生产入口是否仍能构造一份模型切换多会话正文、是否仍有 DeviceStore 的第二保存队列，检查侧聊内容是否进入共享保存端。准入治理检查平台是否仍需理解 parent、控制权与 compact 的组合才能决定排队，核心的状态表是否同时约束投影和命令。

针对变化成本的反例是“再修改一次导航规则”和“再增加一个客户端”。前者应由窗口关联和核心目录负责，编辑模型无需新增会话分支；后者消费核心能力投影，不复制队列政策。API、绑定和窄行为检查提供可重复的约束。证据与剩余事项在实施结束后补入本页。

## 已删除的第二写入路径

Mac 普通会话的配置编辑原本已经走 ComposerContext 的目标 CAS，但 ConversationStore 仍保留普通会话 changeNextTurn／selectNextTurnRuntime 分支，经 DeviceStore.keepChoices 写旧 intent API。实查生产界面和命令均不使用这些分支，测试中的同名调用也已经是 ComposerContext。现在删除这组普通写入、moveChoices 和 Mac Transport 包装，仅保留名称明确的侧聊临时选择方法。预览以合成 snapshot 的模型为初始事实，不额外模拟一次保存。共享核心中其它平台仍使用的 intent API 保留，Mac 读取其投影作为初始化来源。

这项删除使正文和明确配置都不再拥有 Mac 内的第二持久写入口。运行时 lastChosen 仍是单独的使用记录，与目标的明确选择寿命不同；新建策略改由实例配置保存。

## 实例配置的提交边界

新建策略使用 application-api 的 typed codec 写入 RuntimeInstance.settings，与执行环境和 ACP 启动选项共用已有实例提交。Mac 保存后的回调写入与 Windows 的第二次调用已删除。lastChosen 仍表示最近使用，带 Adapter Type 后只对同类型实例有效；核心拒绝迟到的旧类型写入。普通 API 与表单共享策略格式、模型、推理强度和权限校验。

旧 composer schema 1 必须通过一次性迁移转为 schema 2，新建策略先归入实例文件，再提交只含最近使用记录的 composer 文件。中断恢复依赖保留的旧源及原始备份，不在应用中增加双写。真实迁移延后。细节归[迁移说明](../../docs/development/migrations.md#运行时新会话策略归属)。

## 能力与读取来源的归属

原生协议、路径与历史格式随各 Harness 变化，adapter 继续拥有协议实现。侧聊策略已归入 `RuntimeVariant.side_chat`，每个适配器必须明确其实现策略或不支持。NativeSession 按该策略分派，application 用同一事实计算 `RuntimeTypeDescriptor.can_side_chat` 并校验打开／发送，Mac 菜单和侧聊运行时选择消费描述。原先两个核心 RuntimeKind 支持列表和 Mac 支持列表已删除，禁用实例也在两侧被拒绝。新增侧聊实现只需要声明策略及完成 adapter 的原生操作。

列表、项目与回退投影共用 `RuntimeSourceKey`。它由实际 reader／ACP launch builder 的纯解析配置构造，生产、查询及失效使用同一来源身份。名称、默认策略及 Velune 网关／提供商变化可以复用历史缓存。归档按来源分组，每组校验一次，按身份查找的回退共享来源标记。来源切换后拒绝迟到结果和旧客户端归档，读取失败统一清理对应索引、项目与回退。客户端上次列表由 `ListedProjection` 一起持有条目和来源，查找、管理及关联会话标题等消费者经同一访问入口校验，关闭了旧客户端列表绕过来源约束的路径。

执行配置具有独立的 `execution_configuration`。核对实际执行 builder 发现，Pi 的 `sdkHelper` override 只参与执行配置，历史 reader 使用随应用提供的 helper。这一现有差异要求两个身份各自表达依赖。执行配置与网关失效分别负责在途快照和后续准备。完整契约见[浏览与执行准备](../../docs/design/conversations.md#浏览与执行准备)。

开发约束已在[结构变化的验收](../../docs/development/validation.md#结构变化的验收)补充。今后涉及状态归属的改动，既要证明行为，也要说明旧写入与协调的退出；用一个真实的后续变化检验需要共同修改的责任。类型、可见性与少量不变量检查承担可执行约束，文档维护跨单元承诺。不会通过持续增加任务报告或扫描禁用字符串替代代码边界。
