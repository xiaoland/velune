# 迁移与交付边界复核

## 清单与判断

当前已有普通配置 schema、速度模型变体、composer 内容／目标拆分、退役适配器和宽度比例的一次性脚本。它们在显式重装入口启动新版之前执行，各自排他锁、预览和幂等；应用打开遇到未知格式仍明确报告错误。Transport 的退避控制重复失败风暴，迁移负责恢复可用数据，两者承担不同责任。

0.159 退役按真实 CLI 版本选择现成 0.166，转换实例及已删除实例留下的关联段，保留原生 ID。普通 Adapter Type 编辑不改写原生来源，不借本次迁移建立类型间关系。先前同名条目已确认是旧 CLI 列出新版本内部 attached threads，按名称或 fork 标志过滤会错误隐藏真实会话，因此未采用。

## P1 中断后跳过平台缓存

首次把旧草稿／窗口输入导入共享目录时，原实现先写 schema2 catalog，再转换 Mac／Windows／Android 缓存。与已有 schema1 catalog 的转换不同，这条首导路径未保存组合格式恢复点。缓存阶段失败后重跑，程序只看见 schema2，并因缺少恢复点跳过剩余转换，输出已完成。原共享输入没有丢失，但恢复缓存仍是旧格式，重开会失败或缺失本地未同步选择。

修复把初次导入也纳入同一恢复协议。

- 先完成附件复制，再原子写入私有的组合格式恢复点，随后提交新目录。
- 新目录提交前失败，重跑使用恢复点中的原 owner／InputID，继续同一次转换。
- 新目录提交后失败，重跑继续转换平台缓存，不覆盖已提交目录。
- 更早脚本留下的 schema2／无恢复点状态，仍转换旧缓存并保留 pending 选择；缺少可靠旧修订时保持未知基线，由现有冲突处理接续。

没有引入应用自动迁移或新的通用迁移框架。

## 验证

证据在 `target/verification/architecture-review-20261105/`。

- `migration-recovery-before.log` 复现共享目录提交后重跑完全跳过缓存的旧行为。
- `composer-migration.log` 三项通过，覆盖提交前中断的身份连续、提交后续接、旧中断目录缺少恢复点时保留正文／pending 选择；每项均核对再执行不改变结果。
- `migration-integration.log` 既有六项通过，覆盖 serviceTier、未知数据拒绝、锁、私有备份、Codex 退役和完整 runner 与本次恢复协议组合。

仅修改合成目录。用户明确暂缓真实迁移，本轮保持日常应用运行。
